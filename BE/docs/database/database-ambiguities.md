## Decided

### A-01. Sign-off of D01-D22

Confirmed by you. The spec's Part 1 still says approval is pending, so you may want to update that sentence.

### A-02. Table list

The 13 proposed tables are the V1 scope.

### A-03. Physical names

snake_case table and column names, including `users` and `class_id`.

### A-04. Primary key type

`BIGINT GENERATED BY DEFAULT AS IDENTITY`.

### A-05. `ENUM` implementation

`VARCHAR` with `CHECK` for enum-like values. `app_security_log.action` is the one approved exception (A-21).

### A-06. Time types

`completed_at` is `TIMESTAMPTZ`, overriding `TIMESTAMP NULL` in spec 2.1 and following 0.1. Sessions use `session_date DATE`, `start_time TIME`, `end_time TIME`, as Vietnam local values. D08's comparison works directly on these.

### A-07. Class soft deletion

**Final decision, confirmed by you.**

| Topic | Decision |
|---|---|
| **Physical delete** | **Kept, as TR05 defines it.** `DELETE /classes/{id}` is allowed only for a `DRAFT` class that has never had an enrollment, and it also removes that class's sessions |
| **Soft delete** | **Not implemented in the MVP.** No API, flow or service performs a soft delete |
| **`class_offering.deleted_at`** | **Kept in the schema.** Nothing sets it, so it's always `NULL` during the MVP |
| **Other deletion behaviour** | None added |

**In the database:** foreign key `fk_enrollment_class` blocks physically deleting a class with any enrollment row, including `CANCELLED` ones, which matches TR05's "never had an enrollment".

**Query filters:** 0.4, D09, TR08-TR10 and TR18 refer to deleted classes, so queries still filter on `deleted_at`. These filters have no effect during the MVP.

**Limitation:** `class_code` is unique across all rows. Adding a soft-delete action later would be a new business decision, including its rules and whether a deleted class's code can be reused.

### A-09. Optimistic locking

| Field | Purpose | Visible to clients? |
|---|---|---|
| `session.attendance_version` | Detects stale bulk attendance saves (TR14) | Yes, as `version` in `GET /sessions/{id}/attendance` |
| `class_offering.grading_version` | Detects stale bulk score saves (TR15) | Yes, as `version` in `GET /classes/{id}/results` |
| `class_offering.version` | JPA `@Version`: safety net if a flow updates the row without its lock | No, never in a DTO |

This resolves the earlier conflict with TR14, TR15 and 0.4. Details are in [database-design.md](database-design.md#10-version-fields).

### A-10. How results link to enrollments

Composite FK `(student_id, class_id)` to `enrollment`. It proves that an enrollment exists, not that it's `ENROLLED`, so the service must still check that.

**In JPA:** `AssessmentResult` and `GradeAuditLog` can only be built from an `Enrollment`, and they have no `Enrollment` field, which keeps loading lazy. Details are in [database-design.md](database-design.md#composite-foreign-keys).

### A-13. One profile per account

Resolved by D04, with TR01 and TR10. `UNIQUE (user_id)` on both profile tables.

### A-16. Initial values and defaults

No flow in the spec activates a new record, so a record starting inactive would be stuck until an Admin found it.

| Column | Default | Consistent because |
|---|---|---|
| `users.is_active` | `TRUE` | TR01 has no activation step, and login rejects inactive accounts; `false` is reached through `/users/{id}/status` |
| `student.status` | `'ACTIVE'` | TR04 only moves to `SUSPENDED` or `INACTIVE` by Admin action; TR10 requires `ACTIVE` |
| `instructor.is_active` | `TRUE` | TR03 describes only "ngừng nhận lớp" as `false`; TR07 requires `true` |
| `course.is_active` | `TRUE` | TR02 describes only "ngừng sử dụng" as `false`; TR05 requires active |
| `room.is_active` | `TRUE` | TR06 describes only stopping use; sessions require active |

**Exceptions: these must not default to active.**

| Column | Value | Why |
|---|---|---|
| `class_offering.status` | `'DRAFT'` | TR05 creates classes as `DRAFT`; publishing is a checked step |
| `class_offering.grading_status` | `'DRAFT'` | Stated in 2.1 |
| `enrollment.status` | No default | TR10 always sets `ENROLLED` explicitly |
| `attendance.status` | No default | D16 needs a real mark. A default would hide missing attendance and affect D15's rate |
| `session.attendance_locked` | `FALSE` | Stated in 2.1 |
| `assessment_result.final_status` | `'IN_PROGRESS'` | TR15; set only at confirmation |

### A-17. Email case sensitivity

Unique on `LOWER(email)`, so `Foo@x.com` and `foo@x.com` count as duplicates and return `USER_DUPLICATE`. How the email is stored isn't changed.

### A-21. Security log structure

- **Columns:** `id`, `action`, `username`, `ip_address`, `details JSONB`, `created_at`.
- **`action`:** a Java enum holds the 24 actions in spec 0.6, with no database `CHECK`, so a rejected insert can't lose a security event. The enum only protects writes made through the application.
- **`username`:** stored only when it matches an existing account, using the account's own value; otherwise `NULL`. This keeps a password typed by mistake out of the log, and allows narrowing to `VARCHAR(50)`, matching `users.username`.
- **Effect on TR18:** Admins see no username for attempts on accounts that don't exist, but the IP address, time and counts remain.
- **`details`:** must never contain passwords, hashes, tokens or cookies. This is for implementation, with no schema effect.

### A-22. `created_at` and `updated_at`

Added where technically appropriate. Usage is in [database-design.md](database-design.md#11-created_at-and-updated_at).

**Not added, and outside the V1 scope:** `room.name`, `course.description`, `student.phone`, `class_offering.cancelled_at`, `session.unlocked_by`, `session.unlocked_at`. The spec doesn't require them, and a later migration can add them.

### A-25. Race between confirm and unlock

Unlock locks `ClassOffering`, then `Session`, then re-reads `grading_status`. Because TR16 confirm also takes the `ClassOffering` lock first, unlock waits and then correctly returns `GRADING_CONFIRMED`. This follows the order in spec 0.5 and needs no schema change. It needs a concurrency test alongside SEC-TC-203.

## Technical defaults applied

These don't change business behaviour.

### A-11. Surrogate or composite keys

Surrogate `id` on `attendance` and `assessment_result`, each with a unique pair. Composite PK on `instructor_course`.

### A-12. Target of `*_by` columns

`users(id)` for all seven, since Admins have no profile table. Role checks stay in the service.

### A-20. IP address type

## Default applied, business question remains

### A-14. Columns the spec describes without naming

**Applied:** `student.homeroom_class`, `instructor.department`, `instructor.phone`, `room.is_active`, with no format check.

**Still a business question:**

- Are "lớp sinh hoạt" and "khoa" free text or defined lists?
- Does `phone` have a required format?
- Is a room only active or inactive?

**Limitation:** a defined list would need a migration and a new table.

### A-15. Missing lengths and types

**Applied:** the `VARCHAR` lengths for `email`, `full_name`, codes and `semester`, `TEXT` for reasons, `NUMERIC(5,2)` for `min_attendance_pct` and `NUMERIC(4,2)` for `pass_score`.

| Item | Design follows | Still a business question |
|---|---|---|
| `credits`, `duration_hours` | `INT`; the spec says only `> 0` | Can they be fractional, such as 1.5? Changing to `NUMERIC` later is a simple migration |
| `session.topic` | Nullable; the spec gives only a maximum length | Is a topic required? |
| `semester` | Free `VARCHAR(20)`; the spec says only not empty | Is there a required format? |
| Maximum length of reasons | No limit; the spec gives minimums only | Should there be a cap? |

### A-26. Rate-limit storage

**Applied:** in memory, with no table. This holds for one application instance.

**Still a question, before TR01:**

- D03 says "30 request/phút/IP", while TR01 applies it within login ("Vượt 30 lần đăng nhập/phút"). Does it cover login only, or every API?
- Will production run more than one instance?

## Unresolved, following the literal spec

No behaviour is invented for these. V1 is applied as it stands, so any schema change they need must be a new migration.

### A-08. Cancellation deadline

- **Spec:** D05: "bắt buộc nhập, ≤ start_date". TR12: "now ≤ cancel_deadline", showing "[ngày giờ]".
- **Unresolved:** whether 18:00 on `start_date` is a valid deadline.
- **Design:** `TIMESTAMPTZ NOT NULL`, with a `CHECK` that its Vietnam-local date is at most `start_date`. This applies D05 literally and allows that time.
- **Limitation:** if 00:00 is chosen instead, the `CHECK` must be tightened by a migration, and any existing rows would need correcting first.

### A-24. Values after a state change

- **Spec:** says nothing about clearing `return_reason`, `submitted_at`, `submitted_by`, `locked_by`, `locked_at` or `unlock_reason`.
- **Design:** nothing is cleared unless the spec says so, as with `cancelled_at` in TR10. No `CHECK` forbids either choice.
- **Limitation:** an old `return_reason` can remain after re-submitting. Decide before TR14 and TR16 if the UI would show it.

### A-27. Clearing a score

- **Spec:** TR15: "điểm là null hoặc nằm trong [0..10]", and "Khi đủ cả 2 điểm thì tính total_score". D18: editing an existing value requires a reason.
- **Unresolved:** whether `null` clears or leaves a score unchanged, whether clearing needs a reason, and how `total_score` is recalculated.
- **Design:** the columns allow `NULL`, and `grade_audit_log.new_score` can record a clear. The proposed `CHECK` is **not** applied.
- **Limitation:** a stale `total_score` is possible while grading is `DRAFT`. TR15's submit check requires both scores, and TR16 recalculates totals at confirmation, so a stale total can't reach a confirmed result. **It needs an answer before TR15**, because the PUT handler must treat `null` one way or the other.

### A-28. Rounding method

- **Spec:** D14: "round(midterm × w1 + final × w2, 2)". TR16: rate "làm tròn 2 chữ số". No method is named.
- **Unresolved:** whether `HALF_UP` is the officially accepted method.
- **Design:** no schema effect.
- **Limitation:** it decides a pass only on an exact tie, which default weights of 0.4 and 0.6 can't produce, but others can. **It needs an answer before TR15.**
